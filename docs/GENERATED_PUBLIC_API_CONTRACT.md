# Generated Verse Public API Contract

Status: Current v4.5.0-preview.1 source contract; local manual-testing preview, not a published release.

This document defines the one supported Verse surface generated by UEFN Transaction Manager. The managed Verse file is regenerated from project data and must not be edited manually. Creator-authored gameplay, save logic, and reward effects belong in the creator's own Verse.

Current generation imports `/UnrealEngine.com/Marketplace`, following the namespace move in UEFN 42.20. Regeneration with this version requires UEFN 42.20 or newer. Existing generated files using the old Fortnite namespace remain compatible aliases in current editors; the updated import removes their deprecation warnings without changing public UTM identities.

## One canonical API

For new records, generated public symbols derive from each persisted `verseKey`, not from its editable display name. An existing project may explicitly persist a `publicIdentity` captured from its published managed Verse source when its catalog key no longer describes the public API. That identity includes the generated API stem, metadata/entitlement/price/offer stems, and the configured module/device/file names used to qualify the generated paths. Managed manifests also persist the generated module/device configuration, so reopening the bridge cannot silently fall back to stale local settings and rename a published path. Transaction Manager does not generate compatibility alias branches or a selectable API mode: one record has one effective generated identity.

The managed-data schema is independent of generated symbol names. `schemaVersion` remains the persisted manifest marker; supported schema versions 2, 3, and 4 continue to load. Obsolete generated-API metadata and old persisted purchase-event fields are tolerated while reading and omitted from newly generated manifests.

### Existing-project public identity adoption

The `adopt_existing_identity` operation is the only supported way to import a published identity. It is accepted only inside an `existing-project` migration with a confirmed parity table and an explicit stable target ID, object kind, catalog `verseKey`, and complete public-identity override. Generic create/update operations reject supplied identity hints so a stale import cannot be silently normalized into a new API.

UTM derives the requested and effective structured identities before applying the cloned patch. It rejects invalid or conflicting Verse keys/stems, conflicting qualified paths, incomplete parity, and any requested/effective mismatch without changing the live draft. If the catalog key changes, the former key is added to `retiredVerseKeys` and bundle/storefront offer references are updated atomically. A dry run returns the current, requested, and effective identity evidence; the real apply must use the same revision and guarded migration activity. The generated manifest carries the override so reopen and regeneration retain the adopted paths.

## Canonical architecture decision

Transaction Manager does not generate a `UEM` namespace or a second type facade. The supported integration facade is the placed generated device and its canonical public events and methods. Verse supports nested modules, but nesting the generated Marketplace declarations would add another qualification step without improving the normal device-centric integration flow. It would also change every internal Marketplace type reference and require live compiler proof for nested module visibility, cross-module casts, offer construction, and dynamic `MaxCount` access.

The current module and type layout is retained because it follows the shape used by Epic's Marketplace examples and keeps the generated file directly readable. The `<public>` markers on the generated Marketplace declarations describe their current Verse reachability and the requirements of the generated Marketplace definitions. They do not make those declarations supported Transaction Manager integration API. Transaction Manager developers should not bypass the device's UI locking, subscriptions, reconciliation, logging, and result-handling helpers by calling raw generated Marketplace types directly.

The live Verse Workflow Server was used for release verification. The current source structure remains unchanged because the canonical device facade, Marketplace declarations, casts, offer construction, dynamic MaxCount access, and logging all compile successfully in the selected UEM_Demo project. The generated device remains the supported integration surface.

## Representative inventory

The representative fixture in `tests/public-api-fixture.ts` contains four entitlements, one alternate offer, three bundles including a dynamic bundle, two focused storefronts, restrictions, bindings, and auto-consume. It generates 114 explicit `<public>` declarations, 11 UEFN-exposed `@editable` binding arrays, and one private device-level `@editable` runtime debug toggle. The binding arrays use stable role names such as `AccessPass_PurchaseTriggers`, `AccessPass_SuccessTriggers`, `AccessPass_PurchaseButtons`, `AllOffersStore_OpenButtons`, and `CoinStore_OpenTriggers`. Success trigger arrays are output bindings: durable and non-auto-consumable offers fire them from authoritative Granted, while auto-consume offers fire them only from authoritative Consumed; the await and callback APIs carry authoritative quantity.

| Category | Fixture count | Supported surface |
| --- | ---: | --- |
| Icon, metadata, entitlement, price, and offer declarations | 59 | Generated Marketplace plumbing. Public in the current source, but not supported Transaction Manager integration API |
| Entitlement events | 14 | Three public suspending await functions per entitlement, plus `Consumed` for each consumable, with private native event backings |
| Callback registration | 14 | Named `Subscribe<Stem><Boundary>Event` methods for the same notifications |
| Callback lifetime | 2 | A device-prefixed UTM subscription handle type and its idempotent `Cancel()` method |
| Grant and consume helpers | 6 | `Grant<Stem>` and consumable `Consume<Stem>`, returning `logic` |

| Focused storefront helpers | 2 | `Open<StoreStem>` |

Generated device classes remain placeable UEFN devices without a public class declaration. Editable trigger, button, and storefront arrays are editor configuration rather than a promise that external Verse should mutate them.

### Generated module and type inventory

The representative complex fixture emits these top-level declarations:

| Top-level declaration | Current visibility | Generated use | Supported directly by UEM |
| --- | --- | --- | --- |
| `EntitlementIcons` | `<public>` module | Makes configured texture references resolvable from the generated file and other project modules | No. Asset names come from project content and are not a stable Transaction Manager API |
| `<InfoModule>` | `<public>` module | Holds generated metadata modules and localized `Name`, `Description`, and `ShortDescription` messages | No. Metadata is consumed by generated entitlement and offer definitions |
| `<EntitlementsModule>` | `<public>` module | Holds the castable `basic_entitlement` base and concrete durable or consumable entitlement classes | No. Generated reconciliation, queries, Grant, Consume, and dynamic bundle code use these types |
| `<PricesModule>` | `<public>` module | Holds generated V-Bucks price constants used to build Marketplace price dimensions | No. Prices are offer-construction plumbing |
| `<OffersModule>` | `<public>` module | Holds primary, alternate, static bundle, and dynamic bundle offer classes | No. Generated purchase and storefront helpers construct these for Marketplace calls |
| `UEMLogChannel` | Internal class | Provides the generated device logger channel | No |
| `<DeviceClass>` | No `<public>` class declaration | Placeable creative device that owns runtime state and the supported public methods and events | Yes, through the generated device instance |

For the representative fixture, the 59 non-device public declarations are 1 icon module, 33 metadata declarations, 6 entitlement declarations, 9 price declarations, and 10 offer declarations. The generated device contributes the remaining 39 public events and methods. The total is 98 explicit `<public>` declarations.

The inventory applies to the configured module names, so a project may show names such as `ManagedEntitlements`, `ManagedOffers`, `ManagedTransactionPrices`, and `ManagedEntitlementInfo`, or the names configured for that project. The classification does not depend on those names.

`EntitlementIcons` is intentionally not promoted to a stable Transaction Manager asset contract. Developers may reuse a texture in their own Verse when they independently know the project asset path, but Transaction Manager does not guarantee generated icon member names across asset replacement, folder changes, or project configuration changes.

## Supported developer API

For an entitlement with stable key `durable_entitlement`, the generated device exposes:

```verse
Transactions.OpenDurableEntitlementPurchase(Player)
Transactions.GetDurableEntitlementCount(Player)
Transactions.HasDurableEntitlement(Player)
```

Transaction Manager's generated notification API uses native user-created Verse `event(t)` values internally. Each signal-capable backing event is private. Verse 42.20 rejects aliasing an instance member to a public `awaitable(t)` view, so the generated device exposes small public suspending await functions instead:

```verse
<Stem>_GrantedSignal:event(tuple(player, int))
<Stem>_RemovedSignal:event(tuple(player, int))
<Stem>_ReconciledSignal:event(tuple(player, int))
Await<Stem>GrantedEvent<public>()<suspends>:tuple(player, int) = <Stem>_GrantedSignal.Await()
Await<Stem>RemovedEvent<public>()<suspends>:tuple(player, int) = <Stem>_RemovedSignal.Await()
Await<Stem>ReconciledEvent<public>()<suspends>:tuple(player, int) = <Stem>_ReconciledSignal.Await()
<Stem>_ConsumedSignal:event(tuple(player, int))
Await<Stem>ConsumedEvent<public>()<suspends>:tuple(player, int) = <Stem>_ConsumedSignal.Await()
```

The `Consumed` signal and await helper are generated only for consumable entitlements. The generated `Consume<Stem>` helper queues a player/entitlement/quantity intent before calling native `ConsumeEntitlement`; the signal is emitted only when the authoritative entitlement-change stream reports a matching negative delta. A failed or expired request is removed without emitting `Consumed`, and a direct/native removal can have other causes, so `Removed` is not a proof of explicit successful consumption. Immediate-use migration consequences must await `Consumed`; inventory-bearing consumables should not be auto-consumed.

The generated implementation signals only the private backing events. External Verse waits for the next recurring notification with `.Await()`:

```verse
WatchGranted()<suspends>:void =
    loop:
        Grant := Transactions.AwaitDurableEntitlementGrantedEvent()
        HandleGranted(Grant)
```

Transaction Manager offers both await functions and named callback registration methods, backed by native `.Await()`. It does not add an `event.Subscribe` extension. Epic-provided Creative device/listenable events such as button, trigger, and playspace events are separate APIs and may support `.Subscribe()`. One positive delta signals only the `Granted` backing event. One negative delta signals the generic `Removed` backing event and, only for the matched portion of a pending generated consume intent, the consumable's `Consumed` backing event. Reconciliation signals only the `Reconciled` backing event, with the current owned count, including zero. No redundant player-only event families are generated.

For callback delivery, use `Transactions.Subscribe<Stem>GrantedEvent(OnGranted)`, `Subscribe<Stem>RemovedEvent`, `Subscribe<Stem>ReconciledEvent`, or the consumable-only `Subscribe<Stem>ConsumedEvent`. The callback signature is `(Payload:tuple(player, int)):void`. Save the returned `<deviceClassName>_event_subscription` and call `Cancel()` when the gameplay listener ends. Cancellation is idempotent; checks suppress delivery after cancellation and after the transaction device ends. Registration after device end returns an inactive handle. All callback await tasks also terminate on transaction-device end.

These are UTM handles, not native `cancelable` values. Callbacks cannot suspend; explicitly spawn project-owned suspending work if needed. Notifications are not replayed: register early, use ownership/count queries for current state when attaching late, and use Reconciled plus live Granted/Removed callbacks for durable mirrors. Need Help provides copyable examples based on the persisted public identity. This implementation works on UEFN 42.40 and avoids extension-overload conflicts with the native subscriptions announced for 43.00; native 43.00 behavior remains untested.

`Grant<Stem>` and consumable `Consume<Stem>` are suspending public helpers returning the native Marketplace operation result as `logic`. Non-positive quantities return `false` without calling Marketplace. A `true` result reports the Marketplace operation boundary; `Consume<Stem>` additionally creates a pending correlation that can emit `Consumed` only for a matching authoritative decrease. Gameplay should use the canonical notification for its semantic boundary rather than a grant or consume result.

`Get<Stem>Count` queries current Marketplace state for the concrete entitlement and returns zero when no matching result exists. `Has<Stem>` returns whether that current count is greater than zero. Alternate offers share the parent entitlement queries; bundles and storefronts do not get ownership queries.

Player-start reconciliation makes one `GetPurchasedEntitlements` query against Transaction Manager's generated castable `basic_entitlement` base. The returned concrete entitlement instances are classified locally, counts are aggregated, and every managed private `<Stem>_ReconciledSignal` is signaled, including zero for an absent entitlement. This batch path is separate from the public concrete-entitlement query helpers, which remain fresh current-state queries. Auto-consume remains attached only to positive entitlement-change grant processing; reconciliation does not consume inventory.

### Upcoming native subscriptions (43.00)

Epic's [42.40 release notes](https://dev.epicgames.com/documentation/fortnite/42-40-fortnite-ecosystem-updates-and-release-notes) announce that `event(t)` becomes subscribable by default in **43.00**. Conflicting user-defined `Subscribe` extension methods must be removed; native `event.Subscribe` returns `cancelable`. This is an upcoming API change, not evidence that every 42.x editor supports it.

A disposable probe compiled on 42.40 on 2026-10-16 confirmed that native `event.Subscribe` is unavailable (3506), and returning an `event` as `listenable` is incompatible (3510). The probe was removed and the project compiled cleanly afterward.

This does **not** mean callback subscriptions are impossible before 43.00. Epic's [Verse fields event tutorial](https://dev.epicgames.com/community/learning/tutorials/woOK/fortnite-using-verse-fields-events-in-a-umg-user-widget) and the UI template implement them with a spawned recurring `Await()` loop, a callback, and a cancellation event. An equivalent helper specialized to UTM's `tuple(player, int)` payload, exposing a named callback registration method and preserving the private backing event and existing await method, compiled on 42.40 with zero diagnostics. It returns a custom cancellation object; this probe did not establish compatibility with the native `cancelable` interface. A generic helper variant encountered compiler limitation 3502 for that payload, so the template helper should not be assumed to work unchanged in every generated context.

UTM could provide named callback registration helpers now without adding an extension named `event.Subscribe`, avoiding the announced 43.00 name conflict. This is a possible integration UX improvement today, implemented using await tasks; it is not evidence of a performance improvement. The current generator still emits its existing await API, and the disposable helper probe was removed after compilation.

UTM generates private native events and public `Await<Stem>…Event()` methods, with no custom `Subscribe` extension. The announced change does not require renaming or removing those methods. Keep the current contract for existing consumers and 42.x projects.

Once the 43.00 compiler is available, an additive receive-only `listenable(tuple(player, int))` accessor could offer direct subscriptions for ownership-driven HUD, access, and progression updates. Validate the accessor's effects and instance-member access with that compiler before shipping it. Do not expose the backing `event` or its `Signal` method: callers must not fabricate transaction notifications. Store returned `cancelable` values and cancel them at the owning device's end. Preserve distinct `Reconciled`, `Granted`, `Removed`, and consume-correlated `Consumed` boundaries. Subscriptions do not replay reconciliation and callbacks cannot suspend; initialize late listeners from the authoritative ownership helpers and spawn suspending work explicitly. Benchmark before claiming a performance improvement over await loops.

### Durable lifecycle contract

`Reconciliation establishes initial truth. Generated delta events keep current truth current.` The generated device's internal `ReconcilePlayerEntitlements` implementation is not an external integration API; project Verse uses the public `Await<Stem>ReconciledEvent()`, `Has<Stem>`, and `Get<Stem>Count` surface to initialize its own state after player start.

For a durable entitlement, creators may opt into the separate `<Stem>_OwnershipConfirmedTriggers` binding. During that player's reconciliation pass, UTM fires the assigned trigger exactly once when the reported owned count is greater than zero; it does not fire for zero ownership and does not replace the purchase/grant `Success Triggers` binding. This is a no-code join/access hook for effects such as VIP or access-pass setup. More advanced ownership behavior remains in Verse using the existing `Reconciled`, `Granted`, and `Removed` APIs.

For a durable entitlement whose ownership affects live gameplay, UI, access, permissions, progression, multipliers, toggles, or another session-scoped behavior, a project integration must do both of the following:

1. Initialize the external mirror/cache from the authoritative reconciliation path during player initialization.
2. Maintain a persistent await loop for `Await<Stem>GrantedEvent()` for the integration's lifetime and update the external state immediately for a same-session acquisition. A join-only flag, successful initial query, or reconnect check is not synchronization.

If the project needs ownership loss/revocation and the current generated contract supports it, use the actual `Await<Stem>RemovedEvent()` path as well. Do not invent a removal API. A durable with no live gameplay consequence that is queried ad hoc through authoritative helpers may explicitly omit a mirrored listener.

This lifecycle rule is separate from consumable semantics: immediate-use gameplay effects wait for `Await<Stem>ConsumedEvent()`, while durable `Granted` is an ownership delta and never a consumption boundary.

Dynamic remaining-quantity bundles are generated from the same source configuration as their static bundle offer. Name, Description, ShortDescription, duration and odds disclosure, icon, price, restrictions, and configured entitlement offer variant remain shared; only the runtime `Offers` quantity changes. The supported dynamic model is one entitlement entry at quantity 1, with remaining quantity calculated at purchase time from the authoritative generated `MaxCount` and current ownership. Zero remaining quantity does not call `BuyOffer` and releases the Marketplace UI lock. Nested and multi-entry dynamic bundles are rejected by validation.

Dynamic remaining bundles are direct-purchase-only. Transaction Manager omits them from the all-offers storefront and rejects explicit storefront membership because a static storefront offer cannot safely display or calculate player-specific remaining quantity. Static bundles retain their configured entitlement contents and alternate-offer references; a bundle's configured price remains the price of the bundle rather than the selected content offer.

Storefront composition is persisted in one `storefrontMembership` object. `allOffers` is the ordered explicit collection behind `OpenAllOffersStore`; `focused` contains the ordered collections behind each `Open<StoreStem>` helper. Entries identify a concrete primary entitlement offer, alternate offer, or static bundle by stable internal references. New primary offers and static bundles default into `allOffers`; new alternates and dynamic bundles do not. Duplicate entries are normalized, deleted offers are removed from every collection, and focused-store deletion removes only that store definition. Older manifests without explicit global membership are migrated from their historical static catalog composition and rewritten in the new model.

`Open<Stem>Purchase` is the guarded purchase entry point for each entitlement, alternate offer, and bundle. Internal `ExecutePurchase` performs the shared suspending Marketplace call for every concrete offer, including dynamic offers after their remaining-quantity preflight. `OpenAllOffersStore` and `Open<StoreStem>` are guarded storefront entry points. Lower-level `Show…` functions and shared execution helpers remain internal and are not public compatibility APIs.

For runtime-priced entitlements and alternates, and for bundles with runtime price or quantity fields, the integration contract reports the fully qualified `<OffersModule>.<Stem>RuntimeOptions` type, its generated fields, and the guarded `Open<Stem>Purchase` signature. Contract examples use that qualified type and the correct one-argument or two-argument helper shape. The optional `dynamicOfferFactory` field is also fully qualified and explicitly marked as a lower-level generated-offer construction API; external callers should use the device purchase helper instead.

Every generated runtime-priced catalog uses one shared exact `IsValidRuntimePrice` predicate. It accepts only whole V-Bucks values from 50 through 5000 in increments of 50; the generated balanced allow-list is emitted once in the Offers module and reused by every runtime offer factory.

Paid-random classification remains on entitlement metadata. Odds are optional inside Transaction Manager and are included in generated descriptions only when supplied; accurate odds must still be disclosed to players before purchase through Transaction Manager or another clear island disclosure.

## Project-data compatibility

Project-data compatibility is intentionally separate from generated public API compatibility. Transaction Manager preserves valid persisted `verseKey` values, `publicIdentity` overrides, `retiredVerseKeys`, entitlement and bundle references, storefront configuration, and supported schema loading. Missing, malformed, reserved, and duplicate keys are repaired deterministically and surfaced as project-data diagnostics. A valid key such as `starter_bundle2213124124` remains unchanged unless an explicit existing-project adoption intentionally corrects that catalog key while retaining the published identity.

Old manifests may contain fields from temporary pre-release API experiments, including generated API markers, compatibility flags, diagnostics, and purchase-event names. Transaction Manager ignores those obsolete fields, preserves the actual catalog data, and regenerates the current canonical API. Newly created and cleaned manifests do not write them.

Transaction Manager still refuses to import an unmanaged Verse file because guessing its structure could lose data. A managed file is always regenerated from its embedded project manifest.

## Deliberate boundaries

The current implementation preserves shared Marketplace UI execution and locking, stable identity rules, project schema support, paid-random disclosure guidance, restriction behavior, `GetMinPurchaseAge`, query helpers, Grant/Consume result behavior, auto-consume, and authoritative entitlement event processing.

UEFN editables use the current native `@editable:` metadata block with localized `ToolTip` and `Categories` messages. Categories are emitted as a flat native category path: root (`ENTITLEMENTS` or `STOREFRONTS`), stable object display label, then role (`Purchase Triggers`, `Purchase Buttons`, `Success Triggers`, `Ownership Confirmed`, `Open Triggers`, or `Open Buttons`). Display names affect category text and tooltip text only.

The generated device also exposes `EnableDebugLogging:logic = false` under the `DEBUG` category. It is a device configuration property, not a supported callable API symbol. When enabled in UEFN, internal `LogDebug`, `LogWarning`, and `LogError` helpers route diagnostics through the generated logger with `[UEM][Severity]` prefixes. Routine lifecycle, interaction, reconciliation, entitlement-delta, and Marketplace flow messages are debug-gated; warnings and errors remain visible with debug logging disabled. No generated logging helper is `<public>`.

Purchase triggers are supported deliberate-interaction entry points. Transaction Manager passes the triggering player to `Open<Stem>Purchase`, while creators remain responsible for wiring a trigger behind a deliberate player interaction. Purchase buttons are the straightforward recommended binding: an interaction passes the button's player to the same canonical helper. Both callbacks remain thin and use the existing in-flight-safe public entry points.

Passive Mutator Zone purchase bindings and the old automatic-zone-prompt setting are no longer generated. Old manifests and imported project settings containing those fields load safely, ignore the obsolete values, and show a non-blocking migration warning. Existing custom editable-name fields are also tolerated and ignored. The global storefront intentionally remains a button binding while focused storefronts retain their existing trigger binding.

The release audit confirmed that the generated Verse source is visible in UEFN and compiles cleanly. The generated device is obtained through UEFN's Content Browser placement workflow. The selected UEM_Demo acceptance run did not produce a device instance for editable-assignment persistence, so that runtime boundary remains unverified and must not be inferred from source tests or compilation.

The current product intentionally keeps the existing `ManagedEntitlements`-style modules, `_entitlement` and `_offer` class suffixes, and price identifiers. Existing-project identity adoption can retain a legacy module/class/helper path through explicit persisted identity and module configuration; it does not emit a `UEM` namespace or generated API compatibility branches. The product also does not emit purchase zones, automatic prompts, or implicit storefront membership. Storefront membership is explicit project data, and launcher discovery progressively searches fixed local drives while excluding automatic network, removable, and optical-drive crawling.
